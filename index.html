Architecture, data model & testing

Layered Spring Boot architecture — every request passes the JWT filter before reaching a controller.

Data model

  • User1 — NOrdera user places many orders
  • Order1 — NOrderItemcascade ALL, eager fetch
  • OrderItemN — 1Productprice snapshot at purchase
  • User1 — NCartItemlazy fetch, JSON-ignored
  • CartItemN — 1Producteager fetch for display

Implementation notes

  • Security: stateless JWT (jjwt) with a OncePerRequestFilter, BCrypt hashing, and role-based access separating ROLE_USER from ROLE_ADMIN. Custom AuthenticationEntryPoint and AccessDeniedHandler return JSON rather than HTML error pages.
  • Payments: Razorpay order creation followed by server-side signature verification on POST /api/orders/verify-payment — the client is never trusted to confirm a payment.
  • Error handling: a @RestControllerAdvice global handler maps ResourceNotFoundException and BadRequestException onto a consistent ApiError body.
  • Testing: 86 tests across 13 classes — service unit tests with Mockito, @WebMvcTest controller slices, @DataJpaTest repository tests, and a full end-to-end workflow test.
  • Deployment: multi-stage Dockerfile; an EnvironmentPostProcessor rewrites Render’s DATABASE_URL into JDBC form at boot.

Architecture, data model & testing

Interface-and-implementation service layer, with a scheduled job driving reminder emails.

Data model

  • User1 — NRegistrationone row per signup
  • Event1 — NRegistrationcapacity enforced in service
  • RegistrationUNIQUE(user_id, event_id)DB-level guard against double booking
  • EventN — NSpeakerjoin table event_speakers
  • UserenumRoleSTRING-persisted, not ordinal

Implementation notes

  • Data integrity: duplicate registrations are blocked by a composite @UniqueConstraint on (user_id, event_id) — enforced by the database, not just application code, so a race between two requests still cannot double-book.
  • Many-to-many: events and speakers are joined through an event_speakers table with LAZY fetching to avoid loading speaker graphs on list views.
  • Scheduling: EventReminderScheduler runs on @Scheduled and dispatches reminder emails via spring-boot-starter-mail.
  • Layering: every service is split into an interface plus an Impl class, so controllers depend on abstractions and tests can substitute mocks cleanly.
  • Testing: 72 tests across 12 classes, run against an in-memory H2 database so the suite needs no external services. Actuator is exposed for health checks.

Architecture, data model & testing

Document-oriented persistence — Spring Data MongoDB rather than JPA.

Data model

  • usersdocument@Document("users")seeker or employer role
  • jobsdocument@Document("jobs")holds employer reference
  • job_applicationsdocumentseeker × jobguarded by DuplicateApplicationException
  • UserenumRoleJOB_SEEKER / EMPLOYER
  • JobrefpostedByemployer id stored on the document

Implementation notes

  • Persistence: document-oriented storage on MongoDB Atlas via MongoRepository — deliberately different from the JPA projects, so the data model is denormalised rather than joined.
  • Notifications: SmsServiceImpl wraps the Twilio SDK to send real-time SMS when an application status changes; the phone number is collected at sign-up.
  • Authorisation: a CurrentUserProvider resolves the authenticated principal, and ForbiddenOperationException stops an employer from touching another employer’s postings.
  • Domain errors: typed exceptions — DuplicateApplicationException, EmailAlreadyExistsException, ResourceNotFoundException — are translated to HTTP status codes by a global handler.
  • Honest gap: this project has the thinnest test coverage of the three; expanding it is the next thing on my list.
